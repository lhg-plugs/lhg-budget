# lhg-budget-import：账单导入五步法

> **合规声明**：本方法论仅用于记账与预算分析，**不构成任何投资建议**；涉及投资决策请咨询持牌专业人士。

## 1. 何时使用 / 何时不用

**用**：用户给了一个账单 CSV（银行 / 支付宝 / 微信导出），要把它变成干净、可分析的统一账本。

**不用**：
- 用户只给了截图或 PDF 账单 → 先转成 CSV（或手工录入关键行），不要硬套本流程。
- 用户想做的是"规划下个月花多少" → 去预算预警方法论（`lhg-budget-alert`），不是导入。
- 没有真实账单、想"先编个样子" → 停下。本流程第一铁律：**无真实数据，不出账本**。

## 2. 输入与输出

**输入**：1 个 CSV 文件（任意编码、任意分隔符、任意列名）。

**输出**：统一账本 `ledger-YYYYMM.csv`，列固定为：

```
日期,对方,分类,收支,金额,备注,来源文件
2026-10-31,星巴克臻选,,支出,42.00,拿铁,alipay-202610.csv
```

- `分类` 可为空（交给分类方法论补）。
- `收支` 只取 `收入` / `支出` 二值。
- `金额` 为正数，方向由 `收支` 列表达（避免"负的支出"这种歧义）。

## 3. 分步方法论

### 第 1 步：编码探测（三级 fallback）

1. 先按 **UTF-8 严格模式**读前 64KB。成功 → 记为 `utf-8`。
2. 失败 → 按 **GB18030** 重读（支付宝网页版、部分银行导出的中文账单是 GBK/GB18030）。成功 → 记为 `gb18030`，并在报告里提示"建议转存为 UTF-8，下次免探测"。
3. 仍失败 → **判定乱码文件**，停止。不许"将就解析"：乱码硬解只会产出错误金额，比没有数据更危险。请用户去原 App 重新导出（支付宝：我的→账单→导出；微信：服务→钱包→账单→导出）。

### 第 2 步：分隔符识别

1. 取表头行，分别数 `,`、`;`、`\t`、`|` 的出现次数，取最大值者为分隔符。
2. 用该分隔符解析全部数据行：若超过 20% 的数据行列数 ≠ 表头列数 → **结构损坏**，停止并报错（常见原因：备注里有未转义的逗号、Excel 另存时混入换行）。修复方式：让用户用原 App 重导，或手工修那几行。
3. 表头出现重复列名 → 告警（取第一列，其余列在备注里说明）。

### 第 3 步：列名映射（三源对照表）

先找**日期列**、**金额列**（二者缺一不可，找不到就停，这是硬门）：

| 语义 | 支付宝账单常见列名 | 微信账单常见列名 | 银行账单常见列名 |
|---|---|---|---|
| 日期 | 交易创建时间、交易时间 | 交易时间 | 交易日期、记账日期 |
| 金额 | 金额、交易金额 | 金额(元) | 借方发生额 / 贷方发生额、交易金额 |
| 方向 | 收/支 | 收/支 | 借/贷（借=支出，贷=收入） |
| 对方 | 交易对方、对方 | 交易对方、商户 | 摘要、对方户名 |
| 分类 | 交易分类 | —（微信无） | —（银行无） |
| 备注 | 商品、备注 | 商品、备注 | 备注、用途 |

映射策略：
- 列名**包含**关键词即命中（如"交易创建时间"命中"交易时间"）。
- 一个关键词命中多列 → 取第一列，其余进备注。
- **方向列缺失时**：用金额正负判断（正=收入，负=支出，取绝对值进金额列），并在预览卡里明确告诉用户"方向由正负号推断，请核对"。
- 银行"借方/贷方"双金额列：借方有值→支出，贷方有值→收入，合并为一列。

### 第 4 步：清洗（脏数据四件套）

1. **金额**：去掉 `¥ ￥ , 空格 ' "`；全角数字转半角（`４２.００`→`42.00`）；`(100)` 括号形式记为负；保留最多 2 位小数，多出的告警。
2. **日期**：统一为 `YYYY-MM-DD`。`2026/10/31`、`2026-10-31 12:00:00`、`31/10/2026` 都认；**同一文件出现 2 种以上日期格式** → 列出样本请用户确认主格式，不许静默混用。
3. **空行/合计行**：全空行跳过；含"合计""总计"的行跳过并计数告知。
4. **解析失败行**：金额/日期任一解析失败 → 整行进"失败清单"，不丢弃、不硬填，预览时如实展示。

### 第 5 步：去重与预览确认

去重键 = `(日期, 金额绝对值, 对方)`：
- 同一文件内重复 → 保留第一笔，其余标"疑似重复导入"。
- 与目录下已有账本比对 → 命中则提示"可能与 ledger-YYYYMM.csv 中第 N 笔重复"，由用户决定。

**预览确认是强制环节**，落盘前必须给用户看：

```
导入预览：alipay-202610.csv（gb18030，已转码）
共 128 笔 ｜ 2026-10-01 ~ 2026-10-31
收入 ¥12,000.00（3 笔） ｜ 支出 ¥8,432.50（125 笔）
前 10 笔：……
⚠️ 3 笔疑似重复  ⚠️ 2 笔金额解析失败  ⚠️ 方向由正负号推断
确认导入吗？
```

用户确认 → 写 `ledger-YYYYMM.csv`；用户否决 → 告诉他怎么修（重导/手工改）再来一次。

## 4. 反模式（不要这样做）

- ❌ 乱码文件"差不多能看"就硬解析 → 金额错一位，报表全错。
- ❌ 列数对不齐时静默丢列 → 用户永远不知道丢了什么。
- ❌ 预览环节跳过，直接落盘 → 重复导入、方向颠倒无人发现。
- ❌ 把"交易关闭/退款中"的状态行当成真实收支 → 先看状态列，有"交易关闭"先过滤。
- ❌ 用文件名猜月份代替用数据里的日期 → 跨月账单一抓一个错。

## 5. 自检与反馈

**质检门**（每次导入后自问）：
1. 总笔数、日期范围、收支总额能否在原文件里找到对应（抽查 3 笔）？
2. 有无乱码残留（对方列出现 `???` / `�`）？
3. 去重提示是否都经用户确认？
4. 落盘文件列顺序是否为 `日期,对方,分类,收支,金额,备注,来源文件`？

**标准冒烟用例**：用插件自带的 `fixtures/csv-good/` 跑一遍导入，应零 blocker；用 `fixtures/csv-bad/` 跑，应报出编码/结构/金额类问题且不落盘脏数据。

**一键反馈**：发现映射表缺了某银行/某 App 的列名，或某类脏数据没覆盖 → 到本仓库提 issue（标题格式：`[import] <银行/App> 列名缺失`），附上脱敏后的表头行即可。

## 附：三源实战对照（常见列名速查）

### 支付宝（网页版账单下载）
典型表头：`交易号,商家订单号,交易创建时间,付款时间,交易对方,对方账号,商品名称,金额,收/支,交易状态,交易分类,备注`
注意：
- 编码多为 GBK，按第 1 步走 GB18030 fallback。
- `交易状态` 列先过滤"交易关闭"，再解析。
- `金额` 列可能带千分位逗号，清洗时先去逗号再转数字。

### 微信（账单导出）
典型表头：`交易时间,交易类型,交易对方,商品,收/支,金额(元),支付方式,当前状态,交易单号,商户单号,备注`
注意：
- `金额(元)` 列名带括号，映射时用"包含匹配"。
- `当前状态` 为"已全额退款"的行 → 按退款处理（见分类方法论），不计入支出。
- 微信导出多为 UTF-8，偶见带 BOM，csv 模块可自动兼容。

### 银行（以常见借记卡账单为例）
典型表头：`交易日期,记账日期,摘要,交易金额,借方发生额,贷方发生额,余额,对方户名`
注意：
- 借方发生额 = 钱出去 = 支出；贷方发生额 = 钱进来 = 收入。不要搞反。
- `摘要` 里常是"财付通-美团"这类组合，分类时取"-"后面的部分匹配商家。
- 部分银行金额列只有一列"交易金额"，正负号表方向，无方向列时走第 3 步的正负推断。

### 常见坑位清单
1. Excel 打开 CSV 再保存 → 编码变了、日期变了。**永远用原文件**，不要过 Excel。
2. 账单跨月（如 9-25~10-25）→ 按日期拆到自然月再出月报。
3. 同一笔在支付宝和银行卡都出现（快捷支付）→ 只保留支付侧（支付宝），银行侧标"内部转账"去重。
4. 文件名月份 ≠ 数据月份 → 以数据里的日期为准。

### 补充：多文件合并导入
- 用户一次给 3 个文件（支付宝+微信+银行）→ 每个文件独立走五步法，再合并。
- 合并时用去重键跨文件比对，快捷支付的重复只保留支付侧。
- 合并后的 `ledger-YYYYMM.csv` 按日期排序，`来源文件` 列保留出处，方便溯源。
